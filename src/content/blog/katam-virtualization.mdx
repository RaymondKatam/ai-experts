Every home lab has a moment when the tools stop feeling like tools and start feeling like weather: something that happens *to* you. Mine came on an ordinary evening, staring at the same "No valid subscription" dialog I had dismissed a few hundred times, while trying to remember which repository file I had edited after the last upgrade, and why my cluster had decided it no longer had quorum.

None of this is a scandal. Proxmox VE is an excellent piece of software. It is free, it is stable, and it has carried countless labs and production estates, including mine for a long time. If it works for you, keep using it.

But I had stopped *enjoying* my infrastructure. And for someone who spends his working days talking about infrastructure, that felt like a warning light worth paying attention to.

## What tired actually meant

It was never one big problem. It was friction that kept adding up:

- **Living around the edges.** The subscription prompt, swapping the enterprise repository for the community one, small post-install rituals that every guide tells you to do and nobody explains.
- **A platform shaped like a server, when I wanted one shaped like a cloud.** I wanted projects, quotas, roles and API tokens as the *default* way of working. I wanted Terraform and Ansible to be first-class, not an afterthought.
- **Security that is opt-in.** I wanted every VM to start life in a default-deny network posture, with east-west rules expressed as intent ("web may reach db on 5432"), not as a firewall I had to remember to switch on.
- **Leaving should be easy.** If I built a VM on my platform, I wanted to be able to hand it to someone running VMware or Hyper-V tomorrow, as an OVA or a VHDX, without a weekend of conversions.
- **Curiosity.** I wanted to understand every layer, from the KVM ioctl to the OVN flow table to the Ceph placement group. The best way to understand a system is to build one.

So I stopped tweaking and started building.

## Meet Katam Virtualization

Katam is a virtualization platform for any x86-64 server. It doesn't reinvent the hard parts: the hypervisor, the storage and the network fabric are mature open-source projects that already run some of the largest clouds in the world. What Katam adds is the part I always wanted to own: **the control plane**.

### What it does today

| Area | What you get |
|---|---|
| **Compute** | Linux, Windows (UEFI, Secure Boot, TPM 2.0) and BSD guests, GPU passthrough, live migration |
| **Storage** | Ceph RBD with three replicas and copy-on-write clones, or local disks for a single box |
| **Networking** | VLAN bridges or OVN overlay networks with distributed routing, NAT and default-deny security groups |
| **Access** | Projects, quotas, four roles (admin, operator, viewer, auditor), API tokens, Active Directory and SAML SSO |
| **Images** | Import qcow2, raw, VMDK, VHD/VHDX and VMware OVAs; templates; export back out as OVA, VHDX or qcow2 |
| **Resilience** | Node health checks with a witness for a second opinion, BMC fencing over Redfish, automatic HA restart |
| **Disaster recovery** | DR plans with test, planned and disaster modes, on Ceph stretch clusters or RBD mirroring |
| **Data protection** | Scheduled, quiesced snapshots with retention locks, plus immutable copies to S3 Object Lock |
| **Operations** | Declarative stack files, YAML runbooks with dry run and rollback, cost showback, rightsizing and reports |

## Three design decisions I'm proud of

**1. Fencing before failover, with a witness in the room.** The most dangerous moment in any HA system is deciding a node is dead when it is merely unreachable. Restart its VMs elsewhere too early and two copies of the same disk are suddenly being written at once. Katam asks a small witness for a second opinion, powers the suspect node off through its BMC, *confirms* it is off, and only then restarts its workloads. Boring, deliberate and safe.

**2. Snapshots you can't delete, even as admin.** Ransomware crews have learned to go after backups first. Katam snapshots can carry a retention lock that nobody can shorten or remove, and the platform refuses to delete a VM while a lock still protects it. For a copy that lives outside the cluster entirely, Katam writes to S3 buckets with Object Lock in compliance mode, where even the bucket owner can't delete data before its time.

**3. An honest exit door.** Katam never holds your VMs hostage. A stopped VM exports as a VMware OVA with a proper OVF descriptor and stream-optimised VMDK, as a Hyper-V VHDX, or as plain qcow2 for Proxmox and OpenStack. Coming in, VMware OVAs pass through virt-v2v so the right drivers are injected. Platforms should earn your loyalty, not trap it.

## Why it installs like an appliance

Katam ships as a single bootable ISO, about 600 MB, that installs **with no internet access at all**. The kernel, server firmware, KVM, libvirt, Ceph, OVN, the controller's Python stack and the Katam packages are all on the disc.

You boot it from USB or your server's virtual media, choose a role (node, controller, all-in-one or witness), pick a disk and a network, and set an admin password. A few minutes later you have a working host. For racks of identical servers there is an unattended mode driven by boot parameters, so you can install ten nodes as easily as one.

Under the hood it's Ubuntu 24.04 LTS. That's a deliberate choice: Katam's value is the control plane, and I would rather stand on five years of security updates from a mature distribution than maintain a kernel of my own.

### Get running in five steps

1. **Prepare the firmware.** Enable VT-x and VT-d (Intel) or SVM and IOMMU (AMD), and turn Secure Boot off on the host.
2. **Write the ISO** to a USB stick with balenaEtcher or `dd`, or mount it through your server's BMC virtual media.
3. **Boot and answer the installer:** role, OS disk, management network, admin account.
4. **Join the nodes** to the controller with `katam-node-setup` and the controller's SSH key.
5. **Sign in** at `http://<controller-ip>:8080`. The first admin password is waiting in `/root/katam-initial-admin.txt`.

One box is enough to try it in all-in-one mode. Three or more servers unlock Ceph, HA and live migration. Check your download against the `.sha256` file on the release page, and see the [install guide](https://github.com/RaymondKatam/katam/blob/main/docs/INSTALL.md) for the full walkthrough.

## An honest status report

Katam is version 0.4: young software built in evenings and weekends. The installer, web UI, API, access control, image import and export, HA restart, snapshots and metering have been exercised end to end. Ceph at scale, OVN micro-segmentation, BMC fencing, DR mirroring and directory sign-in follow the documented upstream tooling but have had limited testing across different hardware.

So: run it in a lab, break it, and tell me what broke. Don't put your payroll database on it yet.

## What's next

- A Katam CSI driver, so Kubernetes persistent volumes become hot-plugged Katam volumes
- Rolling upgrades from the UI for every role, not just nodes
- Flow-log visualisation for the micro-segmentation layer
- Wider hardware testing, with your help

Building Katam reminded me why I fell in love with infrastructure in the first place. Every layer I used to treat as a black box now has a name, a log line and a reason. If you've ever felt tired of your own lab, I hope Katam gives you that feeling back, or at least gives you a good weekend of tinkering.
